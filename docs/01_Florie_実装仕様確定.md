## 2 開発の前提

Florieは、一輪挿しの切り花を初めて楽しむ人向けのお世話サポートWebアプリである。主な利用の流れは次のとおり。

ユーザー登録・ログイン → 一輪を登録 → 今日のお世話を確認・完了 → お別れ → お花畑から思い出を振り返る

文系・IT未経験の大学生による、1か月程度の個人開発規模を前提に、設計どおり動くアプリの完成を優先する。完成後はJava・SQL・Spring Boot等の学習教材として利用するため、通常の条件分岐や繰返しで処理を追えるコード、役割が分かる名前、必要な理由を説明する日本語コメントを重視する。

使用技術はJava、Spring Boot、Spring MVC、Spring Data JPA、Thymeleaf、HTML、CSS、SQL、MySQL、Mavenを基本とし、設計書指定のSpring Security・Validationを使用する。Controller → Service → Repository → Databaseの構成とし、必要なEntity・Form・設定クラスを設ける。不要なレイヤー、外部ライブラリ、複雑なフロントエンドやJavaScriptは追加しない。

## 5 画面と操作

### 5.1 主要画面とUIの対応

| 画面 | 基準画像 | 主な役割 |
|---|---|---|
| ログイン | UI01 | メールアドレス・パスワードによるログイン、新規登録への移動 |
| 新規登録 | UI02 | ユーザーニックネーム・メールアドレス・パスワード・確認欄による登録 |
| ホーム | UI03・04 | 現在の一輪と今日のお世話。花なしの場合は登録を案内 |
| 花登録 | UI05 | 8種類から一つを選び、花のニックネームを入力 |
| お別れ確認 | UI06 | 対象の花を確認し、終了を確定またはHomeへ戻る |
| お花畑 | UI07・08 | 自分の終了した花を表示。花なしの案内も表示 |
| 思い出表示 | UI09 | 選択した自分の終了した花を振り返る |

ホームの花あり・花なし、お花畑の花あり・花なしは、それぞれ同じ画面の状態として扱う。主要7画面の数は、設計で必要な共通エラー表示を禁止する意味ではない。

### 5.2 お別れの処理

1. ホームのOwakareで確認画面へ移動する。この時点では終了しない。
2. 確認画面には対象の花と確認文を表示する。終了後は元に戻せないことを伝える。
3. Homeで戻った場合は、花・予定・履歴を変更しない。
4. 「お花畑に送る」を押したときだけ、所有者とACTIVE状態を確認して終了日と状態を更新する。
5. 終了後は花なしのホームへ戻り、新しい花を登録できる。

確認画面用にGET `/flowers/{flowerId}/end`と`flower-end.html`を詳細設計へ補完する。確定は既存のPOST `/flowers/{flowerId}/end`で行う。確認画面のためだけのDBカラムやテーブルは追加しない。未完了のお世話が残っていても終了できる。

### 5.3 表示とデザインの基準

ベージュの背景、茶色のヘッダー・下部領域、淡い緑のカード、白いロゴ、丸いナビゲーション、角を丸めたボタン、余白や情報の順序をUI画像にできるだけ合わせる。スマートフォンを中心に、PCでも利用できるようにする。8種類の選択肢や補完した入力欄が画面から欠けないよう、必要な縦スクロールに対応する。

花の画像は例示であり、8種類を見分けられる統一した素材に調整できる。第三者の画像を無断使用しない。パスワード確認欄、ユーザー名、ログアウトは、デザインを保って補完する。

お花畑は自分のENDEDの花のみを終了日の新しい順に表示する。思い出画面でも所有者とENDED状態を確認する。思い出には花の種類・イラスト・花のニックネーム・開始日・終了日を表示し、思い出メモとお世話履歴一覧は表示しない。日付をお花畑一覧にも表示するか、日数を補完するか等の残る表示差分は第8章で区別する。

## 6 データ設計

### 6.1 採用する6テーブル

| テーブル | 役割 | 実装時の基準 |
|---|---|---|
| users | ユーザー情報 | ユーザー自身の`nickname`を保持する |
| flower_types | 花種類マスター | 指定の8種類、イラストの参照先、表示順を保持する |
| care_templates | 花種類ごとのお世話マスター | 名前と周期等を保持する構造。具体的な初期値・件数は未確定 |
| flowers | 登録された一輪 | 詳細設計に`flower_nickname VARCHAR(20) NOT NULL`を追加する |
| care_tasks | 各花のお世話予定 | 花登録時にマスターの名前・周期をコピーし、次回予定日を管理する |
| care_records | 完了履歴 | 完了ごとに記録する。初期版では画面表示しない |

主キー、外部キー、その他のカラム定義は詳細3章を基本とする。基本設計の`recommended_cares`、`user_flowers`、`flower_cares`、`care_histories`を別途作成しない。

### 6.2 詳細設計からの確定差分

- `flowers`に花のニックネーム用の`flower_nickname`を追加する。Flower Entity・登録Form・Service・画面に同じ項目を反映する。
- `memory_note`は追加しない。将来用の空カラム・空の入力欄・表示欄も作らない。
- お花畑専用・思い出専用・確認画面専用のテーブルは作らない。
- お世話説明用の`care_guide_text`は今回の確定差分に含めない。

### 6.3 状態と日付

- 同時にお世話できる花は、1ユーザーにつきACTIVEの1輪まで。終了済みの花は複数保持できる。
- ACTIVEでは`ended_on`がNULL、ENDEDでは終了日が設定済みとなる。
- 花の開始日・終了日、予定日・完了日はDATE／LocalDateを使用する。ユーザー作成日時はDATETIME／LocalDateTimeとする。
- 花の終了は削除ではなく、状態をENDEDにして終了日を保存する処理とする。関連する予定・完了履歴も削除しない。

## 7 初期版の範囲と実装時の確認

登録後の花情報の編集、完了取消、終了取消、履歴の編集・削除は設けない。複数輪の同時管理、写真投稿、お世話の自由追加・編集、通知、外部サービス連携、AI診断、SNS共有、花の自由配置や成長アニメーションなど、設計の対象外機能は追加しない。思い出メモは将来候補に留め、実装の予約はしない。

認証にはSpring Securityを用い、パスワードをハッシュ化して保存する。認証情報からユーザーを特定し、他ユーザーの花や予定を表示・更新しない。データ変更はPOSTとし、CSRF対策、入力検証、Thymeleafのエスケープ、更新後のリダイレクトを設計どおり行う。

花と予定の登録、履歴の登録と次回予定日の更新は、途中だけ成功しないようServiceでトランザクション管理する。一輪制限、未来の予定への完了操作、二重送信、同時操作については実装時に確認する。具体的な排他制御方式は今回固定しない。

実装後はAGENTS第15節に従い、起動・各画面・主要操作・DBの登録取得更新・画面遷移・異常操作を確認する。完成時には起動方法、DB準備、構成、主要機能、テスト方法を残す。本資料の作成時点でアプリのビルド・動作テストを行ったという意味ではない。

## 8 未確定事項と保留事項

### 8.1 お世話設定は今回の仕様確定から除外

以下は未確定であり、実装前整理資料第6・7章の調査結果・提案としてのみ参照する。

- 「水を替える」「茎を確認して整える」を各1日周期にする案。
- 花ごとの具体的なお世話内容、周期、水量、切り方、注意事項、画面説明文。
- UI03の「茎を少し切る」を「茎を確認して整える」へ変更する案。
- 「お世話のヒント」、初日の準備案内、その表示位置・表示方法。
- `flower_types.care_guide_text`等、説明保存用カラムの追加。
- お世話マスターを8種類×2件＝16件とする案。

「翌日に2件表示」「明日から定期のお世話」「初期データ16件」等は、各1日周期の2タスク案に依存するため、確定した表示文・初期値・受入条件として使用しない。設計書の「茎を切る：3日ごと」等の説明例も初期値の根拠にしない。具体的な設定を推測で補完しない。

確定しているのは、承認されたマスターを花登録時に自動設定し、その周期で予定日を計算する仕組みである。お世話設定の確定前でも、後日実装開始の指示があれば土台・認証等から進められるが、お世話の本番初期値の投入と設定に依存する動作の完成判定は保留する。
